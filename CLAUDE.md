# CardLab

Открытый симулятор карточной платёжной сети (упрощённая Visa). Пользователь выпускает виртуальную карту, платит в демо-магазине и в реальном времени видит, как платёж проходит путь магазин → эквайер → сеть → эмитент. Хаос-режим ломает сеть (таймауты, потерянные ответы, дубли, падение эмитента), чтобы показать, что деньги не списываются дважды.

## Архитектура

Модульный монолит на Spring Modulith. Каждый пакет верхнего уровня под `dev.rusl.cardlab` — отдельный модуль:

| Модуль | Роль |
|---|---|
| `issuer` | банк карты: карты, счета держателей, холды, решение одобрить/отклонить |
| `acquirer` | банк магазина: магазины (merchants), приём платежей от магазина |
| `network` | сеть: маршрутизация запросов между эквайером и эмитентом, клиринг и расчёты, stand-in |
| `ledger` | двойная запись: проводки, балансы |
| `merchant` | демо-магазин для фронта (позже) |
| `fraud` | правила антифрода (фаза 4) |

Правила:
- Модули не лезут во внутренние пакеты друг друга. Общение только через публичный API модуля (классы в корне пакета модуля) или через события.
- Тест `ApplicationModules.of(CardlabApplication.class).verify()` должен проходить.

## Предметная область (кратко)

- **Authorization** — эмитент проверяет карту и деньги и ставит **холд** (деньги заблокированы, но не списаны).
- **Capture** — магазин подтверждает списание по холду (полностью или частично).
- **Reversal** — отмена авторизации (например, после таймаута), холд снимается.
- **Refund** — возврат после capture, отдельная операция.
- **Clearing & settlement** — ночной батч: банки рассчитываются друг с другом одной суммой, из платежа удерживаются комиссии (interchange эмитенту, scheme fee сети, остальное эквайеру).
- **Stand-in processing** — если эмитент недоступен, сеть сама одобряет мелкие платежи по заданным правилам.
- Коды ответов в стиле ISO 8583: `00` одобрено, `05` do not honor, `14` неверная карта, `51` недостаточно средств, `54` карта просрочена, `61` превышен лимит, `91` эмитент недоступен.

## Правила кода

- Деньги только `BigDecimal`, scale 2, `RoundingMode.HALF_EVEN`. Никогда `double`.
- Ledger — двойная запись: у каждой операции сумма проводок = 0. Балансы выводятся из проводок, а не правятся напрямую.
- Каждый POST, который двигает деньги, принимает заголовок `Idempotency-Key`. Повтор с тем же ключом и теми же параметрами возвращает тот же результат, с другими параметрами — `409 Conflict`.
- Защита от гонок на балансе: атомарный `UPDATE ... WHERE balance >= ?` или `SELECT ... FOR UPDATE` внутри `@Transactional`. Объясняй, что выбрал и почему.
- Полный номер карты (PAN) не логировать и не возвращать в API, только маску `**** 1234`.
- DTO, команды и события — `record`. Внедрение зависимостей — через конструктор.
- Миграции Flyway: применённую миграцию не редактировать, только новая `V{n}__...sql`.
- Без комментариев в коде: понятные имена вместо комментариев.
- Весь проект на английском: код, имена, комментарии, сообщения об ошибках в API, тексты UI, коммиты, README, миграции. Если комментарий всё же нужен — по-английски, обычный `//`, без оформления (никаких рамок, баннеров, ASCII-разделителей). Со мной в чате — по-русски.
- Не добавляй зависимости в `pom.xml`, не спросив меня.

## План по фазам

1. **Ядро**: карты, счета, авторизация с холдами и отказами, capture, refund, reversal, ledger с двойной записью, идемпотентность, REST API.
2. **Клиринг и расчёты**: ночной батч (`@Scheduled`), комиссии, отчёт по магазину.
3. **Angular**: демо-магазин, живая схема прохождения платежа (SSE), дашборды.
4. **Хаос и антифрод**: задержки, потерянные ответы, дубли, падение эмитента → reversal и stand-in; правила фрода (скользящее окно, скачок суммы, страна).
5. **Шлифовка**: нагрузочный тест (Gatling или k6) с замеренными цифрами, Prometheus + Grafana, Spring Security (API-ключи магазинов), README со схемой и GIF-демо.
